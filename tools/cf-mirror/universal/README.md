# CF Universal Mirror

Generic, owner-controlled mirroring for any accessible Chrome DevTools Protocol (CDP) browser or X11 application on the Linux CF Server. Uses the existing cf-mirror engine: adaptive 20/10/5 FPS MJPEG, JPEG quality levels, mouse and keyboard, viewport fit. The runtime copy adds exact CDP tab selection, X11 authorization discovery and mobile touch forwarding.

## Modes

LOCAL (default): returns a simple numeric URL such as http://127.0.0.1:6200/ . Open it in a graphical web browser running ON THE SERVER (e.g. inside XRDP). No password, public DNS, Caddy configuration or tunnel.

WEB (explicitly requested): returns an HTTPS trycloudflare.com URL, expiration, and a session password. The password is mandatory: if not supplied, a high-entropy one is generated and shown once. Secure HttpOnly SameSite=Strict session cookie, CSRF Origin checks, password-attempt rate limiting, no-cache, and expiration enforced on every request. Expiry kills the web gateway, active streams, inner mirror and cloudflared tunnel. Duration 30 seconds to 24 hours, default 5 minutes for web requests.

No domain/provider allowlist applies to browser navigation. Google/third-party OAuth URLs and redirects are supported as far as Chrome and the identity provider permit; Google may independently reject automated/headless browsers.

## Install

On the CF server as cfserver (no root):

    sh tools/cf-mirror/universal/install.sh

Installed owner shortcut:
    /home/cfserver/.local/bin/cf-mirror-any

ChatGPT can invoke this shortcut via the existing owner-authorized CF Server tool server_exec. Five dedicated cf_mirror_* MCP tools are registered in production; existing original cf-mirror remains unchanged.

## Usage

~~~sh
# list available browser ports/tabs and X11 displays/windows
/home/cfserver/.local/bin/cf-mirror-any list

# local, all tabs and address bar, browser auto-detected by URL/title
/home/cfserver/.local/bin/cf-mirror-any start whatsapp-login --app whatsapp

# entire CDP browser with tab strip, new/close/switch and address navigation
/home/cfserver/.local/bin/cf-mirror-any start browser --cdp 9383

# only this tab (do not show tab toolbar)
/home/cfserver/.local/bin/cf-mirror-any start one-tab --cdp 9383 --tab snapp.taxi

# actual full GUI Chrome browser frame with native tabs/address bar, via X11
/home/cfserver/.local/bin/cf-mirror-any start gui-browser --x11 :121

# generic X11 app discovered by window name
/home/cfserver/.local/bin/cf-mirror-any start wechat --app wechat

# public HTTPS for five minutes, strong autogenerated password
/home/cfserver/.local/bin/cf-mirror-any start login --cdp 9346 --mode web --ttl 5m

# public HTTPS for one hour with caller-supplied password
/home/cfserver/.local/bin/cf-mirror-any start owner-login --x11 :121 --mode web --ttl 1h --password asdffhgfs

# fixed interval, e.g. 10 FPS
/home/cfserver/.local/bin/cf-mirror-any start telegram --app telegram --interval 0.1

# inspect, screenshot and terminate sessions
/home/cfserver/.local/bin/cf-mirror-any status
/home/cfserver/.local/bin/cf-mirror-any screenshot login --out /home/cfserver/mirror.jpg
/home/cfserver/.local/bin/cf-mirror-any stop login
/home/cfserver/.local/bin/cf-mirror-any stop all
~~~

CLI start JSON response includes URL, mode, source, expiration, and (only for web mode) password. The owner should enter website passwords/MFA directly in the mirrored browser, not in chat.

## Capabilities and limits

- With CDP and NO explicit --tab, the UI shows a browser-like toolbar with all tabs, open/close/switch, URL input and Back. Popups bearing openerId can automatically be selected. This toolbar is an emulation: headless Chrome has no native tab/address-bar frame. Switching between browser profiles/ports requires a separate session.
- With --tab, the selector must uniquely match one page. No silent fallback to another target.
- With X11, the current largest visible app/browser window is cropped and centered, including native Chrome tabs. Dialogs overlaying that window are visible; separate top-level popup windows may require selecting another source/adjusting focus. --full explicitly shows the entire display. Use a dedicated X11 display to prevent other windows from appearing.
- CDP Auto-Fit can change target viewport (max 2560x1600); --no-fit turns that off. X11 native display resolution is preserved. Arbitrary exact pixel-resolution presets are not part of this version.
- On mobile, one finger moves the cursor RELATIVELY; tap clicks at cursor; hold opens context menu; double tap double-clicks; flick has inertia. Pinch and two-finger gestures zoom/pan the viewer; at 1x, two-finger slides scroll the app. Only optional special-key controls and native-keyboard activation remain.
- Requires CDP remote debugging or user-readable X11 display and Xauthority. Cannot access root-protected :0, Wayland-only apps, DRM/hardware-protected pixels, or unknown remote native apps without a supported capture interface.
- PUBLIC RISK: whoever knows both a web URL and its password has full remote mouse/keyboard control, can read the mirrored browser and navigate to internal network pages. Strong passwords, short TTLs and a dedicated browser session are recommended.
- LOCAL RISK: loopback is not authentication; another process/user with access to server loopback can access an active local mirror.
- Cloudflare Quick Tunnel provides no fixed hostname or uptime guarantee. The web URL can stop working before its requested duration.
- Baseline cf-mirror runtime is copied, not overwritten. Runtime new features remain isolated from old users.

## 2026-11-15 follow-up: mobile control POST and pre-existing cookie

The earlier mobile form token fix was insufficient: some mobile browsers sent authenticated control requests (`/fit`, `/move`, `/key`, `/api/*`) without a conventional `Origin` header, and `/login` with an existing valid cookie incorrectly fell through to the generic POST origin check. The gateway now routes `/login` through its password+CSRF verification even when an auth cookie exists. Authenticated browser UI (outer and inner viewer) receives a per-session-cookie HMAC CSRF token and sends it using the `X-CF-Mirror-CSRF` header for input/control POSTs. A control request is accepted when the HTTPS Origin matches or when the correct CSRF header is supplied; a valid auth cookie is still mandatory in public mode. No domain allowlist was added and all time limits remain enforced. A safe diagnostic event logs only the route class and presence flags, never passwords, CSRF values or cookie values.

Verified: local outer/inner UI receive matching tokens; no-Origin control with token HTTP 200; without token HTTP 403; foreign-Origin without token HTTP 403; web login CSRF token accepted without Origin (incorrect password HTTP 401), invalid CSRF HTTP 403; unauthenticated public screenshot and control HTTP 401; real Alibaba browser source and public HTTPS health successful. A real phone login with the new URL is pending user validation.

## 2026-11-15: low-latency WebSocket input and adaptive fresh-frame MJPEG

The universal viewer now prefers a long-lived same-origin WebSocket (`/input-ws`) for relative mouse movement. Each movement is sent immediately, without waiting for a previous HTTP response; the backend accumulates bounded deltas and sends an acknowledgment after applying them in X11/CDP. Tap and keyboard commands remain ordered by waiting for movement acknowledgments. HTTP /move-rel continues as a fallback if a browser or proxy lacks WebSocket support. Flick inertia AND velocity-dependent amplification are removed, preserving direct proportional motion.

Public WebSocket connections pass through the existing authenticated gateway. A successful password login cookie, exact same HTTPS Origin, a per-session HMAC CSRF token as a second WebSocket subprotocol, and unexpired TTL are all required; only the loopback /input-ws backend endpoint is forwarded. The backend validates client-masked RFC6455 frames, restricts payload size and delta magnitudes, and never exposes CDP/X11 ports. Raw unauthenticated and foreign-Origin upgrade attempts are rejected with HTTP 403 (HTTP 401 for missing public login).

`stream-manager.mjs` keeps only one pending MJPEG frame, skips new frames when the viewer socket is backpressured, and sends the next frame promptly after motion rather than waiting behind an old buffered image. Auto rate now starts at 10fps and uses 15/10/5fps tiers adjusted with hysteresis for whole-host CPU usage, available memory, event loop lag and dropped network frames. Explicit manual interval remains supported. Browser HUD shows WS/HTTP mode and `/info` includes auto rate, CPU, available memory and dropped-frame count. The original standalone cf-mirror is unchanged.

QA: existing gesture/touch/keyboard tests passed. The actual X11 pointer moved exactly +45,+19 via the local gateway WebSocket with `101 Switching Protocols` and an acknowledgment in 46ms from the server-local test. Missing CSRF and cross-origin upgrade handshakes were each rejected with HTTP 403. Active auto `/info` reported 0.1s, CPU 15%, memory available 10%, dropped frames 0. New public HTTPS URL responds 200 and unauthenticated viewer responds 401; physical user phone latency and authenticated public-tunnel WebSocket still require confirmation.

## 2026-11-15: optional low-latency touchpad circle + demand-driven remote microphone

**Optional virtual pointer:** A bottom-toolbar ⌖ toggle shows/hides an immediate predictive circle separate from the native X11 cursor. Default OFF; tapping ⌖ makes the lightweight 19px ring track the finger's translated relative movements immediately in the phone viewport. Tapping again removes it, while the authentic mouse cursor (arrow/I-beam/hand) remains inside the captured X11 video. The ring does not send extra clicks, alter mouse calibration, or add inertia. Server-confirmed positions resynchronize the hint after motion settles; physical cursor still arrives with the video frame. This follows established optional virtual-mouse patterns in RustDesk and remote cursor visibility controls in AnyDesk, but is a proprietary implementation, not a copy.

**Remote microphone standby (different from dictation):** 🎙 now arms a secure microphone **routing service**. Pressing the button does **not** call getUserMedia and does **not** start recording or illuminate the phone mic indicator. The backend discovers a compatible PulseAudio source `cf_wechat_preboot_mic`, backed by `cf_wechat_preboot_sink.monitor`, and watches recording source-output streams from processes bound to the selected mirrored X11 DISPLAY or CDP browser ancestry. Only when such a remote application opens the source does the server send `capture-needed` over an authenticated /mic-ws WebSocket. The phone then requests Android browser microphone permission if needed, calls getUserMedia, starts MediaRecorder WebM/Opus in 100ms chunks, and sends audio through the same expiring authenticated tunnel. Server decodes with FFmpeg and writes timed 48k mono PCM to the pre-existing PulseAudio null sink via pacat; matching apps record from the virtual mic. Remote app stop -> capture-stop -> Android tracks and recorder stopped while button remains armed. Manual disarm, pagehide or network disconnect stops capture and clears standby. No audio is saved as a file by this service. Uses only pre-existing user PulseAudio, no privileged configuration changes.

**Known bounds:** A microphone permission prompt is expected **when the remote application first starts recording**, not on the standby button press. Web browsers cannot grant microphone permission without capture, and Android may display system microphone indicators during active recording. Requires a browser with MediaRecorder WebM/Opus and getUserMedia (typically modern Chromium-based Android browsers); remote apps must actually open the monitored PulseAudio virtual source, not ALSA directly or a different audio server. Per-app behavior, phone permission prompts, codec compatibility, service work while backgrounded, and latency require physical Android and Telegram/WeChat verification before declaring device support. Recording demand is scoped to processes matching the mirrored X11 DISPLAY/CDP instance. Backend test synthetic tone is not an actual voice recording or message send.

**Security/reliability:** Public `/mic-ws` and `/input-ws` remain protected by the same short-lived authenticated session cookie, signed control token in the WebSocket subprotocol, strict same-origin check and tunnel TTL; WebSocket endpoints stay loopback-bound. CSP connect-src is configured per session to permit only its exact WSS origin because some mobile browsers do not treat 'self' as WSS. The server mic bridge performs no audio handling while merely armed; incoming binary audio is ignored unless a remote application is actively recording. Standby/recording are invalidated when the client closes, half-closes or disconnects. In-flight asynchronous PulseAudio checks use a revision/generation check so delayed results cannot re-arm or start audio after explicit OFF. Queues are bounded; compressed audio chunks are paced in real time.

**Validation:** Node source syntax; existing touchpad/pinch, keyboard/backspace and viewport tests pass; optional ⌖ on/off plus immediate predicted cursor movement test passes. Frontend microphone mock verifies zero getUserMedia requests when armed, exactly one on capture-needed, audio chunk send, track shutdown on capture-stop and manual OFF. Local authenticated `/mic-ws` handshake passed; missing signed token rejected (403); disconnect resets standby. Complete local synthetic WebSocket audio test passed: monitor request -> capture-needed -> paced WebM/Opus binary packets -> PulseAudio source recording received nonzero PCM -> capture-stop -> status OFF. Public HTTPS and anonymous-frame authorization tested separately. Phone-specific microphone permission and actual Telegram/WeChat voice-message workflow are NOT yet tested.
